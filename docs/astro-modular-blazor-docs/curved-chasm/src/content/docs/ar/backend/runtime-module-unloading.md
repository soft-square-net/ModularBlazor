إزالة مسارات وحدة أمر سهل. أما **تحرير ذاكرتها** فيعني أن يجمع وقت التشغيل `AssemblyLoadContext` الخاص بها، وهذا
لا يحدث إلا حين لا يشير شيء في أي مكان إلى أي من أنواعها. وفي ASP.NET Core عدة ذاكرات مؤقتة على مستوى العملية
تفعل ذلك بالضبط.

## كيف عثر على الممسكين

1. فعل الوحدة النموذجية، واستدعها أو ولد مستند OpenAPI الخاص بها إن شئت، ثم فرغها.
2. يتحقق التفريغ من `WeakReference` إلى سياق التحميل بعد عدة دورات لجمع البيانات المهملة.
3. إن بقي حيا، خذ تفريغا للذاكرة واسأل ما الذي يبقي `LoaderAllocator` الخاص بالوحدة حيا:

```bash
dotnet-dump collect -p <pid> --type Heap -o module.dmp
dotnet-dump analyze module.dmp -c "dumpheap -type LoaderAllocator" -c "gcroot <address>"
```

4. إن لم يظهر `gcroot` شيئا مفيدا، **نصف المشكلة**: استدع مكونا واحدا من الإطار في كل مرة حتى يظهر الإمساك، ثم
   **امش على الحقول الثابتة بالانعكاس** بدءا من النوع المشتبه به. فقد يفوت `gcroot` ممسكا تماما (انظر حالة
   `TypeDescriptor` أدناه).
5. أصلح الممسك، وكرر.

## ما الذي أمسك الوحدات، والإصلاحات

| الممسك | الإصلاح |
| --- | --- |
| `JsonOptions.SerializerOptions` في المضيف يخزن بيانات JSON الوصفية لأنواع طلبات الوحدة واستجاباتها، وتنشأ عند بناء نقاط النهاية | تحصل كل وحدة على `JsonOptions` **خاصة بها**، تضبط بإجراءات الضبط نفسها في المضيف، فتموت الذاكرة المؤقتة مع الوحدة |
| حاوية حقن التبعيات في المضيف تخزن كل نوع يطلب منها | الأنواع التي تذكر نوعا من الوحدة لا يحلها المضيف أبدا (انظر [الحاوية الفوقية](/ar/backend/runtime-modules/)) |
| `ParameterBindingMethodCache`، ذاكرة ثابتة لربط معاملات Minimal API. وهي شيفرة مشتركة المصدر: لكل من Http.Extensions وApiExplorer وOpenApi نسخته | تخلى أنواع الوحدة من كل نسخة، بالانعكاس |
| ذاكرات `TypeDescriptor` المؤقتة | خطافات `ClearCache` الخاصة بإعادة التحميل الساخن `[MetadataUpdateHandler]` في الإطار، مع إخلاء `s_defaultProviderInitialized` |
| `ReflectTypeDescriptionProvider._typeData`: بيانات لكل نوع في المزود الافتراضي لـ `TypeDescriptor`، يوصل إليها عبر `TypeDescriptor.s_providerTable` ← العقدة ← المزود. ولا يمسحها خطاف إعادة التحميل الساخن | تخلى بالمرور على سلسلة المزودين (`FrameworkCaches.EvictTypeDescriptionProviders`)، مع جداول ذلك النوع الثابتة ذات مفاتيح Type |
| `EndpointDataSource` على مستوى حقن التبعيات لم يتحدث أبدا، فاحتفظ بنقاط النهاية القديمة (وقدم OpenAPI قديما) | الاشتراك فيه مرة واحدة عند البدء بـ `GetChangeToken()` |
| يحتفظ ApiExplorer بآخر أوصاف حسبها | إعادة حسابها مباشرة بعد إزالة مسارات الوحدة |
| مفردات OpenAPI تخزن معرفات المخططات حسب النوع وسياقات العمليات حسب المعرف | تمسح ذاكراتها عند التفريغ؛ ويعيد طلب المستند التالي بناءها |

### إمساك OpenAPI: عثر عليه بالتنصيف

لمدة طويلة بقيت الوحدة في الذاكرة بعد توليد أي مستند OpenAPI وهي مفعلة، وأظهر تفريغ الذاكرة "لا جذور مدارة". وكشف
التنصيف السبب:

1. استدعاء `EndpointMetadataApiDescriptionProvider` في ApiExplorer مرة واحدة، دون أي شيفرة OpenAPI ودون ذاكرته
   المؤقتة، كان كافيا لإمساك الوحدة.
2. وداخله، كان `TypeDescriptor.GetConverter(moduleType)` وحده كافيا. ويجري `ModelMetadata.IsComplexType` هذا الاستدعاء
   لكل نوع معامل واستجابة.
3. الممسك هو القاموس `_typeData` في المزود الافتراضي `ReflectTypeDescriptionProvider`، ويوصل إليه عبر
   `TypeDescriptor.s_providerTable` ← العقدة ← المزود.
4. لم يبلغ `dotnet-dump gcroot` عن هذا المسار أبدا: أظهر مقابض ضعيفة فقط. ووجده المرور الانعكاسي على الحقول الثابتة.

أصبح التفريغ ثم إعادة التفعيل ثم إعادة توليد المستند ثم التفريغ مجددا يعمل مرارا.

ويحتاج الجمع أيضا إلى صبر: يحرر مخصص المحمل بالمنهيات، لذا ينتظر التفريغ بين دورات جمع البيانات المهملة بدل
الدوران المتواصل. ودوراته الخاصة (نحو ثانية) لا تكفي غالبا تماما: تظهر الوحدة أولا تحت
`GET /api/admin/modules/unloading` ثم تجمع عند الفحص التالي، بعد 2–5 ثوان.

## النتائج مع الوحدة النموذجية

أعيد القياس في 2026-11-11 (Greeting، عملية جديدة لكل تشغيل، تشغيلان لكل حالة):

| ما ولد والوحدة مفعلة، ثم تفريغ | قبل إصلاح `TypeDescriptor` | الآن |
| --- | --- | --- |
| لا شيء (تفعيل، واستدعاء GET وPOST، ثم تفريغ) | جمعت خلال 5 ثوان | جمعت خلال 5 ثوان |
| مستند المضيف (`/openapi/webapi.json`) | لم تجمع بعد 20 ثانية | **جمعت خلال 5 ثوان** |
| مستند الوحدة نفسها (`/openapi/modules/greeting.json`) | لم تجمع بعد 20 ثانية | **جمعت خلال 5 ثوان** |

| سيناريو آخر | النتيجة |
| --- | --- |
| دورات تفريغ وتفعيل متكررة | جمعت في كل مرة |
| الترقيات وتغييرات الإعدادات عبر 8 نسخ ([المختبر](/ar/backend/hybrid-lab/)) | تبقى النسخ المستبدلة غالبا تحت `/unloading` لبعض الوقت؛ وأظهرت تفريغات الذاكرة لاحقا النسخة النشطة وحدها في كل نسخة |

تعيد نتيجة التفريغ ما حدث فعلا (`unloaded` و`gcPasses`)، فلا يخبر المسؤول أبدا أن الذاكرة حررت وهي لم تحرر.

## تحفظات

- معظم الإصلاحات تصل إلى **داخليات الإطار** بالانعكاس. تحقق منها مجددا بعد كل ترقية لـ .NET؛ وتظهر نتيجة
  التفريغ وقائمة `/unloading` فورا متى تعطل أحدها.
- الوحدة التي لها **حالة ثابتة أو خيوط أو مؤقتات** لا توقفها عند التخلص منها لن تفرغ أبدا. يجب أن تحرر الوحدات كل
  شيء في خدمات `IDisposable` / `IAsyncDisposable`.

## التوصية

| العملية | تعامل معها على أنها |
| --- | --- |
| التثبيت والتفعيل وإلغاء التفعيل | حية بالكامل: دون إعادة تشغيل |
| الترقية وتغيير الإعدادات | تبديل حي دون فترة 404؛ وتسترد ذاكرة النسخة القديمة بعد ثوان قليلة |
| التفريغ | تختفي المسارات فورا؛ وتسترد الذاكرة بعد ثوان قليلة، وتؤكد ذلك `/unloading` |
| الاسترداد المضمون للذاكرة | إعادة تشغيل متدرجة، وهي ما يفعله [النشر بنسخ متعددة](/ar/backend/deployment-scenarios/) أصلا |
