يمكن نشر الشيفرة نفسها بطريقتين. تبدأ معظم الأنظمة بالسيناريو A، ثم تنقل وحدات بعينها إلى B.

## السيناريو A: تطبيق موحد معياري بنسخ متعددة

كل حاوية تشغل الصورة نفسها بكل الوحدات.

```text
               load balancer / gateway
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  API #1 [A+B+C]  API #2 [A+B+C]  API #3 [A+B+C]      stateless, same image
        └──────┬───────┴───────┬──────┘
               ▼               ▼
   Redis (cache, keys, locks)  Broker (competing consumers)
               ▼
   Tenant store + tenant databases · Object store
```

**المزايا:** نشر بسيط، وتبقى الاستدعاءات بين الوحدات داخل العملية، وكلفة تشغيل منخفضة.

**الكلفة:** وحدة واحدة مزدحمة توسع التطبيق كله؛ وتسرب ذاكرة أو ارتفاع في المعالج داخل وحدة يصيب الجميع؛ وكل
إصدار يعيد نشر كل الوحدات؛ وتتراكم مجمعات الاتصال (النسخ × قواعد بيانات المستأجرين × حجم المجمع).

### ما يجب مشاركته قبل إضافة نسخة ثانية

كل بند من هذه ينكسر بصمت حين توجد أكثر من نسخة:

| البند | ما يحدث إن أهمل | الحل |
| --- | --- | --- |
| مفاتيح ASP.NET Data Protection | تفشل ملفات تعريف الارتباط ورموز مكافحة التزوير على نسخة أخرى | احفظ المفاتيح في Redis أو قاعدة بيانات أو تخزين كائنات، باسم تطبيق واحد |
| الذاكرة المؤقتة داخل العملية | تقدم النسخ بيانات مختلفة وقديمة | `HybridCache` أو `IDistributedCache` على Redis، مع أحداث إبطال |
| تحديد المعدل | تسمح كل نسخة بالحد كاملا، فيصبح الحد الفعلي N ضعفا | حدد المعدل في البوابة، أو احفظ العدادات في Redis |
| المهام المجدولة | تشغل كل نسخة المهمة | Hangfire أو Quartz بوضع العنقود، أو قفل موزع، أو مجموعة عمال |
| ترحيلات EF Core والبذر | تتسابق النسخ عند بدء التشغيل | شغلها مرة واحدة كمهمة قبل النشر أو حاوية تهيئة |
| SignalR | تصل الرسائل إلى عملاء النسخة نفسها فقط | Redis backplane أو Azure SignalR |
| ذاكرة إعدادات المستأجرين | ترى نسخة واحدة فقط التغيير | خزنها في Redis، وأبطلها بحدث `TenantUpdated` |
| الملفات المرفوعة | تحفظ على قرص حاوية واحدة | تخزين الكائنات فقط |
| الصحة | تصل الحركة إلى نسخة ما زالت تبدأ | فصل `/health/live` عن `/health/ready`؛ ويتحقق ready من قاعدة البيانات والوسيط |

ميزة "سهولة المعاملات" لا تصح إلا إذا تشاركت الوحدات اتصالا واحدا. والوحدات هنا تملك كل منها مخططها و`DbContext`
الخاص بها، لذا يبقى العمل الذري بين الوحدات بحاجة إلى معاملة مشتركة، أو الأفضل إلى
[صندوق الصادر](/ar/backend/communication/)، الذي يستمر في العمل بعد الفصل.

## السيناريو B: مجموعات تنشر مستقلة

تجمع الوحدات في مجموعات؛ لكل مجموعة نسخها وقاعدة توسعها وإصدارها.

```text
Identity API   ×3     login and token refresh; JWTs are validated locally in every service
Sales API      ×4     autoscaled on CPU or requests per second
Inventory API  ×2     two is the minimum for high availability; idempotent stock updates
Workflow API   ×2     saga state in a database, so any replica can resume a workflow
```

**المزايا:** توسع ونشر وعزل للأعطال وتوزيع للموارد، كل ذلك بشكل مستقل.

**الكلفة:** يصبح التتبع الموزع إلزاميا، وتصبح العمليات العابرة للخدمات متسقة في النهاية (تعرض الواجهة حالات
"قيد التنفيذ")، وتحتاج العقود إلى إصدارات، وتحتاج كل مجموعة إلى خط نشر ولوحات مراقبة خاصة بها.

### موازنة الحمل في السيناريو B

| الحركة | الآلية | انتبه إلى |
| --- | --- | --- |
| العميل إلى البوابة | موازن حمل طرفي أو Ingress | إنهاء TLS وجدار حماية التطبيقات يكونان هنا |
| البوابة إلى المجموعة | عنقود YARP لكل مجموعة، بحسب بادئة المسار (`/sales/*`) | وجهة لكل نسخة مع فحص صحتها. خلف عنوان واحد يوازن على مستوى الاتصال (خدمة ClusterIP)، ثبت اتصال YARP الدائم 100 % من الحركة على نسخة واحدة في [المختبر](/ar/backend/hybrid-lab/) |
| خدمة إلى خدمة (gRPC) | موازنة من جهة العميل أو شبكة خدمات | يبقي gRPC اتصالات HTTP/2 طويلة: خدمة Kubernetes عادية من الطبقة الرابعة ترسل كل الاستدعاءات إلى حاوية واحدة. استخدم `Grpc.Net.Client` مع محلل DNS وخدمة headless، أو Linkerd/Istio |
| الرسائل | مستهلكون متنافسون | انظر [موازنة حمل الرسائل](/ar/backend/communication/) |

### ملكية البيانات

**لا تقرأ أي خدمة جداول خدمة أخرى.** مشاركة *خادم* قاعدة البيانات مقبولة؛ أما مشاركة المخطط أو بيانات الاعتماد
فلا. البيانات التي تحتاجها خدمة تصلها عبر واجهة الخدمة المالكة أو أحداثها.

## Scalar وOAuth عبر البوابة

لا يغير اختيار النشر A أو B حد الهوية: تبقى خدمة الهوية مستقلة، وتتحقق كل مجموعة API من JWT. افتح Scalar عبر بوابة YARP الثابتة كي تمر طلبات الواجهة عبر المسار نفسه.

| النشر | رابط Scalar | عنوان OAuth لإعادة التوجيه |
| --- | --- | --- |
| السيناريو A / واجهة الجذر | `http://localhost:5080/scalar/` | `http://localhost:5080/scalar/` |
| السيناريو B / مجموعة sales | `http://localhost:5080/pools/sales/scalar/` | `http://localhost:5080/pools/sales/scalar/` |
| السيناريو B / مجموعة worker | `http://localhost:5080/pools/worker/scalar/` | `http://localhost:5080/pools/worker/scalar/` |

أصل المتصفح لهذه الروابط المحلية واحد: `http://localhost:5080`، لذا تحتاج خدمة الهوية إلى أصل CORS واحد مطابق. أما عناوين إعادة OAuth فتختلف: سجل كل مسار كاملا كما هو. منافذ نسخ Aspire الديناميكية للتشخيص، وليست روابط Scalar أو عناوين OAuth ثابتة. راجع [تشخيص OAuth في Scalar](/ar/backend/auth-implementation/#oauth-في-scalar-بمختبر-hybird).

## ابن لـ B وانشر كـ A

صمم كل وحدة كأنها منفصلة بالفعل، وانشرها داخل التطبيق الموحد إلى أن تحتاج إلى أن تتوسع أو تفشل وحدها. يصبح نقلها
عندئذ تغييرا في النشر فقط. ولا ينجح ذلك إلا إذا تحققت هذه الشروط من اليوم الأول:

1. لا تشير الوحدة إلى غيرها إلا عبر تجميعات `*.Contracts`. افرض ذلك باختبارات بنية (NetArchTest أو
   ArchUnitNET) في CI.
2. لا `DbContext` مشترك، ولا ربط بين مخططات الوحدات، ولا معاملة عابرة للوحدات.
3. تكتب الاستدعاءات الداخلية كأنها بعيدة: غير متزامنة، وكائنات نقل بيانات فقط، ولا كيانات، ولا حالة مشتركة قابلة للتغيير.
4. يختفي النقل خلف العقد: للواجهة نفسها تنفيذ داخل العملية وتنفيذ عبر gRPC.
5. تمر الرسائل دائما عبر الوسيط الحقيقي.
6. واجهات الوحدات خشنة الحبيبات. الواجهة الثرثارة المجانية داخل العملية تصبح بطيئة عبر الشبكة.

تبين [البنية المستهدفة](/ar/backend/target-architecture/) كيف تخدم صورة واحدة السيناريوهين.
