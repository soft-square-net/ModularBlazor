تتواصل الوحدات بطريقتين. اختر بحسب ما يحتاجه المستدعي، لا بحسب العادة.

| المستدعي… | استخدم | مثال |
| --- | --- | --- |
| يحتاج إلى جواب الآن ليكمل | **استعلام** متزامن عبر gRPC (أو استدعاء داخل العملية إن كانت الوحدتان في مجموعة واحدة) | "هل يسمح لهذا المستخدم بتقديم طلبات؟" |
| يريد من وحدة أخرى أن تغير حالتها | **رسالة أمر** غير متزامنة؛ ويعيد المستدعي `202 Accepted` | "احجز المخزون للطلب 42" |
| يعلن عن شيء حدث | **حدث تكامل** بالنشر والاشتراك | `OrderPlaced`، `TenantUpdated` |
| يقرأ بيانات وحدة أخرى كثيرا | **لا هذا ولا ذاك**: احتفظ بنموذج قراءة محلي تغذيه أحداث تلك الوحدة | تحتفظ Sales بنسخة من أسعار المنتجات |

## قواعد الاستدعاءات المتزامنة

- **قفزة واحدة على الأكثر.** أن تستدعي A الوحدة B مقبول؛ أما أن تستدعي B بدورها C فيضاعف زمن الاستجابة واحتمال الفشل. إن ظهرت سلسلة،
  فاستبدل إحدى قفزاتها بنموذج قراءة أو برسالة.
- **حدد دائما مهلة**، وأعد المحاولة مع تأخير عشوائي للعمليات الآمنة فقط، وضع قاطع دائرة أمامها
  (`Microsoft.Extensions.Http.Resilience` أو Polly).
- **المتصفحات لا تتحدث gRPC الأصلي.** يستدعي عميل Blazor البوابة عبر REST/JSON (أو gRPC-Web)؛ أما gRPC
  فللاستدعاءات بين الخدمات فقط.
- **لا تستدع أبدا عبر البوابة العامة من الداخل.** تستدعي الخدمات بعضها مباشرة على الشبكة الداخلية (DNS في
  Kubernetes أو شبكة خدمات).

## الاستدعاء نفسه داخل العملية أو عبر الشبكة

لا تشير الوحدة أبدا إلى تنفيذ وحدة أخرى، بل إلى تجميع `*.Contracts` الخاص بها فقط. ويختار النقل عند بدء التشغيل:

```text
Sales needs ICatalogQueries
   ├─ Catalog runs in the same pool   → in-process implementation (direct call)
   └─ Catalog runs in another pool    → gRPC client implementation
```

لا يتغير المستدعون حين تنتقل وحدة. ولكي يتصرف المساران بالطريقة نفسها، عامل الاستدعاءات الداخلية كأنها بعيدة:
توقيعات غير متزامنة، وكائنات نقل بيانات قابلة للتسلسل، ولا كيانات مشتركة، ولا معاملة مشتركة.

## رسائل موثوقة: صندوق الصادر وصندوق الوارد

يجب ألا تضيع رسالة إن توقفت العملية بين "حفظ البيانات" و"نشر الحدث"، ويجب ألا تطبق مرتين حين يعيد الوسيط
تسليمها.

```text
Producer (Sales)                              Consumer (Inventory)
  ┌───────────────────────────────┐             ┌──────────────────────────────┐
  │ one transaction:              │   broker    │ inbox: seen message id?      │
  │   save order                  │ ──────────► │   yes → acknowledge, skip    │
  │   insert OrderPlaced (outbox) │             │   no  → handle + record id   │
  └───────────────────────────────┘             │         in one transaction   │
         relay publishes outbox rows            └──────────────────────────────┘
                                                  failed N times → dead-letter queue
```

| الجزء | السبب |
| --- | --- |
| جدول **صندوق الصادر** (outbox) في قاعدة بيانات المنتج نفسها | يحفظ الحدث في المعاملة نفسها مع التغيير، فإما أن يحدثا معا أو لا يحدث أي منهما |
| **المرحل** | ينشر صفوف صندوق الصادر إلى الوسيط ويعلمها كمرسلة؛ ويمكن تشغيله على كل نسخة مع قفل |
| **صندوق الوارد** (inbox) أو مفتاح تساوي الأثر | تكتشف الرسائل المعاد تسليمها وتتجاوز |
| **طابور الرسائل الميتة** | الرسالة التي تفشل مرارا تركن للفحص بدل أن تعطل الطابور |
| **الترويسات** | معرف الربط ومعرف المستأجر وسياق التتبع تنتقل مع كل رسالة |

## عقود الرسائل

- تعيش العقود في تجميع `*.Contracts` الخاص بالمنتج، **وتطور بإضافة حقول فقط**. لا تعد تسمية حقل قد يقرؤه
  مستهلك ولا تحذفه.
- سم الأحداث بصيغة الماضي (`OrderPlaced`) والأوامر بصيغة الأمر (`ReserveStock`).
- اجعل الرسائل صغيرة ومكتفية بذاتها: معرفات مع القيم التي يحتاجها المستهلك، لا كيانات كاملة.

## موازنة حمل الرسائل

كل نسخة تستضيف مستهلكا تتنافس على الرسائل، فإضافة نسخ تزيد الإنتاجية، مع حد واحد:

- **Kafka**: التوازي محدود بعدد الأقسام (partitions). أربع نسخ على قسمين تترك نسختين بلا عمل. استخدم معرف
  المستأجر أو معرف التجميعة مفتاحا للقسم لتحافظ على الترتيب لكل كيان.
- **RabbitMQ / Azure Service Bus**: لا حد للأقسام؛ وحين يهم الترتيب، استخدم الجلسات أو مستهلكا نشطا واحدا لذلك
  الطابور.
