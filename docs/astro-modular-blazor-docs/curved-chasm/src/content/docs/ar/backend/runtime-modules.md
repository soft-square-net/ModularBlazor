يبين النموذج الأولي في `src/WebApi/WebApi` أنه يمكن رفع وحدة وتفعيلها وخدمتها **والواجهة تعمل**، وأن كل نسخة في كل مجموعة
تتقارب إلى حالة الوحدات نفسها. إنه شيفرة بحثية: يثبت الآلية ويقيس حدودها.

| المشروع | دوره |
| --- | --- |
| `WebApi` | المضيف. يحمل مجلد `Modularity/` بيئة التشغيل. والصورة نفسها تعمل في كل مجموعة. |
| `WebApi.Contracts` | `IRuntimeModule` و`ModuleManifest`. يشير إليه المضيف، فهو مشترك دائما. |
| `Modules/Core/*` | الوحدات الأساسية (`Identity` و`Tenancy`)، تشحن مع كل إصدار من WebApi. |
| `Modules/Custom/WebApi.Modules.Greeting` | وحدة مخصصة نموذجية. **لا** يشير إليها المضيف: تضغط مخرجات بنائها وترفع. |
| `Modules/Custom/Inventory` | وحدة مخصصة نموذجية مقسمة إلى مشاريع Domain وApplication وInfrastructure. |
| `Aspire/Hybird` | مختبر قابل للتشغيل: بوابة، وثلاث مجموعات، ووسيط، وRedis، وPostgreSQL. انظر [مختبر البنية الهجينة](/ar/backend/hybrid-lab/). |

كل المسارات تحت `src/WebApi/`.

## الوحدات الأساسية والمخصصة

في `src/WebApi/Modules/` مجلدان. تعمل وحداتهما بالطريقة نفسها أثناء التشغيل (سياق التحميل نفسه، والحاوية الفوقية،
والتبديل والبث)؛ ويختلفان في طريقة وصولها:

| المجلد | البناء | الوصول إلى الفهرس | الإزالة |
| --- | --- | --- | --- |
| `Core/` | يبنيها WebApi مع كل إصدار؛ وتنسخ مخرجاتها إلى `CoreModules/<AssemblyName>/` | تزرع بحالة `Active` عند البدء | يمكن إلغاء تفعيلها وتفريغها وإعادة ضبطها، لكن لا يمكن إلغاء تثبيتها ولا استبدالها برفع (`409`)؛ ولا تُرقى إلا بإصدار |
| `Custom/` | تبنى وحدها، خارج إصدار WebApi | يرفعها المسؤول (`POST /api/admin/modules`) | بالكامل: تثبيت وتفعيل وإلغاء تفعيل وتفريغ وإلغاء تثبيت |

- يحمل `Modules/Directory.Build.props` الإعدادات المشتركة للوحدات ذات الطبقات (`<Name>.Domain` و`<Name>.Application`
  و`<Name>.Infrastructure`). ومشروع Infrastructure هو التجميعة الرئيسية للوحدة.
- يعلم `Core/Directory.Build.props` الوحدات الأساسية ويضبط تحزيمها.
- لا يفعل `Custom/Directory.Build.props` سوى استيراد الإعدادات المشتركة: فالوحدات المخصصة ليست جزءا من إصدار WebApi أبدا.
- لا تطبق المجموعة أيا من النوعين إلا إذا تضمنته قائمة `Modules:Enabled` الخاصة بها، أو كانت القائمة فارغة.

## دورة الحياة

```text
upload ─► Install ─► Activate ─────────► Deactivate ─► Unload ─► Uninstall
          │          │                    │             │
          │          ├ load assembly      ├ routes 404  ├ dispose module services
          │          ├ build services     │             ├ evict framework caches
          │          └ map routes (live)  │             └ unload the load context
          └ read the manifest in a throw-away load context, register it in the catalog
```

كل استدعاء إداري يكتب **حالة مرغوبة** في الفهرس المشترك. ثم تتقارب إليها كل نسخة:

| الحالة المرغوبة | يضبطها | على كل نسخة تفعل مجموعتها الوحدة |
| --- | --- | --- |
| `Installed` | التثبيت (وحدة جديدة)، والتفريغ | غير محملة |
| `Active` | التفعيل | محملة؛ ومساراتها مربوطة في مجموعات `Api` |
| `Inactive` | إلغاء التفعيل | تزال المسارات؛ وتبقى محملة إن كانت محملة |
| محذوفة | إلغاء التثبيت | تفرغ وتحذف الحزمة |

- **التثبيت** يحفظ الحزمة، ويقرأ البيان من التجميعة، ويسجله مع إعداداته الافتراضية. وإعادة تثبيت وحدة موجودة
  **ترقية**: تحتفظ بحالة الوحدة وتبدل كل نسخة إلى الإصدار الجديد.
- **التفعيل** يحمل التجميعة، ويبني خدمات الوحدة، ويربط مساراتها. فتجيب فورا.
- **إلغاء التفعيل** يزيل المسارات (404) لكنه يبقي الوحدة محملة، فيكون التفعيل التالي فوريا.
- **التفريغ** يتخلص كذلك من خدمات الوحدة ويفرغ تجميعاتها؛ انظر
  [تفريغ وحدات التشغيل](/ar/backend/runtime-module-unloading/).
- **عند بدء التشغيل** تتقارب النسخة إلى الفهرس، فتعود الوحدات التي حالتها `Active` إلى العمل.

فهرس النموذج الأولي هو `modules.json` مع الحزم، في مجلد واحد تتشاركه كل النسخ؛ أما المضيف الحقيقي فيحفظه في مخطط
الوحدات.

## وحدة

```csharp
public sealed class GreetingModule : IRuntimeModule
{
    public ModuleManifest Manifest { get; } = new("greeting", "Greeting", "1.0.0", "greeting")
    {
        DefaultSettings = new Dictionary<string, string?> { ["Greeting:Prefix"] = "Hello" }
    };

    public void ConfigureServices(IServiceCollection services, IConfiguration settings)
    {
        services.Configure<GreetingOptions>(settings.GetSection("Greeting"));
        services.AddSingleton<GreetingCounter>();
        services.AddScoped<GreetingService>();
    }
}

public sealed class GreetingEndpoints : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app)
    {
        app.MapGet("/{name}", (string name, GreetingService greetings) => greetings.Greet(name));
    }
}
```

تخدم نقاط نهايتها تحت `/api/{RoutePrefix}` (هنا `/api/greeting/...`). وما دامت مسارات الوحدة مربوطة، يكون لها مستند
OpenAPI خاص بها، `/openapi/modules/greeting.json`، يظهر في Scalar على `/scalar`؛ انظر قسم "OpenAPI وScalar" أدناه.

## المجموعات والنسخ

الصورة نفسها تعمل في كل مجموعة. وثلاثة إعدادات تحدد ما تفعله النسخة:

| الإعداد | القيم | الأثر |
| --- | --- | --- |
| `Modules:Pool` | اسم (`core`، `sales`، `worker`) | يظهر في الحالة والسجلات؛ وهو مصدر رسائل البث |
| `Modules:Role` | `Api` (افتراضي) أو `Worker` | `Api` يربط مسارات الوحدات المفعلة؛ و`Worker` يحملها (خدمات ومستهلكون) دون مسارات |
| `Modules:Enabled` | قائمة معرفات وحدات؛ والفارغة تعني الكل | تطبق المجموعة هذه الوحدات فقط وتتجاهل بقية الفهرس |

يصل الاستدعاء الإداري إلى نسخة **واحدة** عبر البوابة. ودون مساعدة لن تعلم به النسخ الأخرى أبدا: قبل وجود البث، كان
تفعيل `greeting` بهذه الطريقة يترك `/api/greeting` يجيب بـ 404 على ثلاث من نسخ مجموعة sales الأربع. لذا فحالة
الوحدات **فهرس مشترك مع بث**:

```text
admin call ─► any replica ─► catalog (modules.json + packages, cross-process lock): desired state per module
                    │
                    ├─► SyncAsync here
                    └─► RabbitMQ fanout "modules.state" ─► every other replica ─► SyncAsync
```

- **الفهرس هو مصدر الحقيقة.** تتم الكتابة تحت قفل بين العمليات. ورسالة `ModuleStateChanged` تقول فقط "تغير شيء
  ما"، فالرسالة الضائعة تصلحها الرسالة التالية، أو المزامنة التي تعمل عند البدء وبعد الاشتراك مباشرة.
- **`SyncAsync` متساوية الأثر.** تفرغ الوحدات التي لم تعد مطلوبة هنا، وتبدل الوحدات التي تغيرت حزمتها أو إعداداتها،
  ثم توصل كل وحدة مفعلة في المجموعة إلى حالتها المرغوبة.
- **تربط كل نسخة طابورها الحصري** بمبادلة البث `modules.state`، فتتلقى كل نسخة كل تغيير. وتتجاهل النسخة رسائلها
  هي: فقد طبقت التغيير بالفعل.
- **البث اختياري.** يفعل حين يضبط `ConnectionStrings:broker` (`builder.AddRuntimeModuleBroadcast("broker")`)؛ والنسخة
  الواحدة دون وسيط تعمل بالطريقة نفسها، دون البث.

### تبديل دون توقف

إعادة التثبيت (`InstalledAt` أحدث) أو تغيير الإعدادات يجعل كل نسخة **تبدل**: تحمل نسخة جديدة، وتستبدل مسارات
القديمة بمسارات الجديدة في تحديث واحد لمصدر البيانات، ثم فقط تحرر النسخة القديمة. لا ترى الطلبات أي فترة 404: في
المختبر، أعادت ترقية مع تغيير إعدادات تحت الحمل 300 من 300 طلب بالرمز 200. وإن فشل تحميل النسخة الجديدة، تحتفظ
النسخة بالنسخة العاملة وتبلغ عن الخطأ.

## أربع مشكلات وحلولها

### 1. جدول المسارات يبنى عند البدء

`ModuleEndpointDataSource` هو `EndpointDataSource` يضاف إلى التطبيق مرة واحدة فارغا. عند التفعيل، يعمل
`ICarterModule.AddRoutes()` الخاص بالوحدة على `ModuleRouteBuilder` خاص، داخل مجموعة مسارات `/api/{prefix}`. تدخل
نقاط النهاية الناتجة مصدر البيانات، فيطلق رمز التغيير، ويعاد بناء التوجيه دون إعادة تشغيل. ويزيلها إلغاء التفعيل
بالطريقة نفسها؛ ويستبدلها التبديل في تحديث واحد.

### 2. حاوية حقن التبعيات مجمدة بعد البدء

الوحدة المثبتة لاحقا لا تستطيع إضافة خدمات إلى حاوية المضيف. `ModuleContainer` **حاوية فوقية** لكل وحدة:

- تبنى خدمات الوحدة (`GreetingService` و`GreetingCounter` و`IOptions<GreetingOptions>`) في الحاوية الفوقية.
- ويأتي كل ما عدا ذلك (`ILogger` وإعدادات المضيف وخدمات الطلب ذات النطاق) من المضيف.
- تعمل كل نقطة نهاية للوحدة و`HttpContext.RequestServices` مضبوط على نطاق للوحدة فوق نطاق الطلب، فتعيش خدمات
  النطاق الخاصة بالوحدة طلبا واحدا بالضبط.
- **أي نوع يذكر نوعا من الوحدة يبنى دائما في الحاوية الفوقية**، حتى `ILogger<GreetingService>`. فحاوية المضيف
  تخزن كل نوع يطلب منها، وذلك التخزين سيبقي الوحدة في الذاكرة إلى الأبد.

### 3. هوية الأنواع عبر سياقات التحميل

تحمل كل وحدة في **`AssemblyLoadContext` قابل للجمع** خاص بها (`ModuleLoadContext`):

- أي تجميعة يشحنها المضيف (الإطار وCarter و`WebApi.Contracts`) تحل من المضيف. وإلا لكان `IRuntimeModule` في
  الوحدة نوعا مختلفا عن نوع المضيف، ولفشل كل تحويل.
- تحمل التبعيات الخاصة بالوحدة (تستخدم الوحدة النموذجية Humanizer) في سياقها الخاص، اعتمادا على ملف `.deps.json`.
- تحمل التجميعات **من البايتات**، فلا تقفل ملفات الحزمة أبدا ويمكن استبدالها بينما ما زالت نسخة تشغل الإصدار القديم.

### 4. يجب أن يتبع OpenAPI المسارات

يسجل مصدر البيانات أيضا كـ `IActionDescriptorChangeProvider`، ويشترك التطبيق عند البدء في `EndpointDataSource`
على مستوى حقن التبعيات. ودون هذا الاشتراك يحتفظ بأول قائمة نقاط نهاية رآها: فيتقادم OpenAPI وتبقى نقاط النهاية
القديمة في الذاكرة.

## OpenAPI وScalar

يعمل OpenAPI في بيئة التطوير، أو في أي مكان مع `OpenApi:Enabled=true` (`OpenApi/ModularOpenApi.cs`). تحصل كل وحدة
مربوطة المسارات على **مستند خاص بها**، ويسرد Scalar المستندات الموجودة الآن.

| العنوان | المحتوى |
| --- | --- |
| `/openapi/webapi.json` | نقاط النهاية المدمجة في المضيف: إدارة الوحدات و`/api/pool` و`/health` |
| `/openapi/modules/{id}.json` | نقاط نهاية وحدة واحدة؛ و**404** ما لم تكن مسارات الوحدة مربوطة على هذه النسخة |
| `/openapi` | المستندات المتاحة الآن: `[{name, title, url, isDefault}]` |
| `/scalar` (ويحول `/` إليه) | Scalar؛ يسرد مبدل المستندات فيه المستندات نفسها، ويعاد بناؤه عند كل تحميل للصفحة |

- **خانة واحدة لوحدات كثيرة.** تصل الوحدات بعد بناء حاوية حقن التبعيات، فلا يمكن تسجيلها كمستندات OpenAPI مسماة.
  يسجل المضيف مستندين: `webapi`، الذي يستبعد كل نقطة نهاية تحمل `RuntimeModuleMetadata` (فلا يلمس أنواع الوحدات
  أبدا)، وخانة داخلية `modules`. يضبط `/openapi/modules/{id}.json` الوحدة المطلوبة في `AsyncLocal`، ويبقي
  `ShouldInclude` الخاص بالخانة نقاط نهاية تلك الوحدة فقط. ويولد المستند عند الطلب عبر `IOpenApiDocumentProvider` ولا
  يخزن مؤقتا.
- **القائمة تتبع المسارات.** تقرأ من نقاط نهاية الوحدات الحية، فتختفي الوحدة من Scalar فور إلغاء تفعيلها أو تفريغها.
- **خدمات الوحدة ليست أجسام طلبات.** يسأل ApiExplorer حاوية المضيف هل المعامل خدمة، والمضيف لا يعرف خدمات الوحدات.
  فيحذف `ModuleServiceParameterFilter` الجسم المستنتج لنقاط نهاية الوحدة التي لم يصرح مندوب طلبها بجسم.
- **خلف البوابة**، المستندات لكل نسخة، فتعرض ما تربطه تلك المجموعة. ترسل مسارات البوابة `/pools/{pool}/**`
  الترويسة `X-Forwarded-Prefix: /pools/{pool}`؛ وتبنى منها عناوين المستندات وعنوان الخادم في كل مستند (ويتجاهلها
  التوجيه). لذا يسرد `/pools/sales/scalar` الوحدة `greeting`، ويبقى "Try it" على `/pools/sales/...`. انظر
  [مختبر البنية الهجينة](/ar/backend/hybrid-lab/).

لم يعد `/openapi/v1.json` موجودا.

## الإعدادات

تنسخ القيم الافتراضية في البيان إلى الفهرس عند التثبيت. ويستطيع المسؤول استبدالها
(`PUT /api/admin/modules/{id}/settings`)؛ فتبدل كل نسخة حملت الوحدة إلى نسخة مضبوطة بالقيم الجديدة، دون توقف. وإعادة
التثبيت تحتفظ بقيم المسؤول للمفاتيح التي لا تزال في الإصدار الجديد.

## ما لم يغط بعد

- جدول وحدات حقيقي بدلا من `modules.json` وملف قفل.
- التفويض على واجهة الإدارة؛ وتوقيع الحزم والتحقق منها.
- تشغيل ترحيلات EF Core الخاصة بالوحدة عند التفعيل، مرة واحدة، خلف قفل موزع.
- الخدمات ذات المفاتيح داخل الوحدات.
- استعادة تبعيات `.nupkg`: اشحن التبعيات في صيغة `.zip` بدلا من ذلك.
- تصريف الطلبات الجارية قبل التفريغ (التبديل لا يحتاج إليه: تبقى النسخة القديمة تخدم حتى تستبدل).

نقاط النهاية والإعدادات وقواعد التحزيم: [مرجع واجهة وحدات التشغيل](/ar/reference/runtime-modules-api/).
